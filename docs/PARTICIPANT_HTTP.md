# Private participant HTTP adapter (checkpoint)

`createParticipantHandler` from `./participant-http` adapts the accepted participant offer registry to Fetch `Request`/`Response`. The trusted host supplies an authenticated human participant Context, current server time and a session-bound random CSRF token through an authentication callback. There is no built-in login, invitation delivery, public server, cookie issuer or identity proofing.

Only four routes exist: GET `/participant/session`; GET `/participant/offer?offerId=...`; POST `/participant/respond` with `{commandId,input}`; and POST `/participant/withdraw` with `{commandId,offerId,expectedConsentRevision}`. Response input has exactly `{offerId,expectedRevision,reviewDigest,response,acknowledged}`. Review uses actual participant-to-subject checks. Withdrawal resolves the participant's accepted offer to its own current consent; it cannot select another consent ID. The adapter exposes no manager resource/offer/rights commands, evaluation of others' records, arbitrary SQL or publication.

All requests require the configured exact HTTPS origin, plus same-origin Fetch Metadata or an exact Origin header on reads. Writes require the exact Origin, same-origin Fetch Metadata if present and constant-time comparison with the authenticated session CSRF token. JSON responses are private/no-store, same-origin, nosniff and contain no authentication credentials or participant mappings. Cross-origin CORS is not enabled. The session route intentionally returns the session-bound CSRF token and local actor/scope to the authorized caller.

Body handling allows uncompressed UTF8 JSON only, bounds actual bytes to 16 KiB and reads to 4096 chunks, has a finite deadline and cancels failed streams without waiting on hostile cancellation callbacks. Authentication is bounded and receives cancellation. Errors use a fixed code allowlist and never expose exception diagnostics. Registry operations already begun are not abandoned or retried automatically; a lost response may follow a committed mutation. Clients must preserve the exact request and command ID and explicitly reconcile it. A returned accepted receipt does not revive withdrawn consent; review supplies the current state.

Checkpoint validation: seven new Fetch/actual-registry/restricted-migration PGlite groups, in addition to existing library tests. Final source review and additional edge cases are in progress. No listening server, reverse proxy, TLS termination, browser/session integration, accessibility, independent database sessions or live participant qualification is claimed. Deployment must authenticate sessions independently, keep actor/mapping authority server-side, apply secure cookies/TLS/CSP and rate limits, present exact terms as inert text, guard against coercion and bind clients to identity changes. The request's Context is supplied by the host, never request JSON or a diagnostic header.
