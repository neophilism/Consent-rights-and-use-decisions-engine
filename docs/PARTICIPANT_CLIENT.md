# Private participant client

`ParticipantClient` from `./participant-client` is an opt-in Fetch client for the accepted participant HTTP handler. It has no runtime Node imports and uses platform Fetch, streams, structuredClone, TextEncoder/TextDecoder and Web Crypto SHA-256. It is a library, not a participant screen, login service or qualified browser deployment.

Construct with an exact HTTPS origin, fixed tenant/project, trusted same-origin Fetch implementation and optional per-exchange timeout (10..30000 ms, default 15000). The host must supply a secure authenticated same-origin session, TLS, CSP and secure cookies. Native browser Origin/Fetch Metadata supply the handler's request admission; a non-browser transport must supply those headers itself without accepting caller overrides. The client sets same-origin credentials, error-on-redirect and no-store. It exposes no invitation, manager, send, rights grant, evaluation or publication operation.

Call `review(offerId)` before every new decision. The returned exact disclosure/terms/warnings must be presented as inert, accessible text. `respond(commandId, { response: 'accept' | 'decline', acknowledged: boolean })` captures the INTERNAL viewed revision/digest and requires explicit acceptance acknowledgement. There is no default decision or automatic write. Caller mutation of returned review objects cannot change the command. After success, review again before further actions; response receipts are historical and cannot establish current permission. In particular, replaying acceptance after withdrawal does not revive consent.

`withdraw(commandId)` uses only the currently reviewed accepted offer's own unwithdrawn consent edition. It cannot select an arbitrary consent ID. Every explicit mutation first obtains a fresh session CSRF token and checks the fixed scope/local actor. Digest and exact-field checks validate the accepted profile, scoped references, immutable terms, deterministic capture binding, current consent content and terminal command result. Those checks establish internal consistency, not identity, informed consent, rights ownership, reading/comprehension or a downstream use authorization.

Before POST, the client retains an immutable command. A transport failure, timeout, invalid result, 503 OR explicit rejection leaves it locked: no replacement decision, review, withdrawal or automatic retry. `resolvePending()` is the only explicit replay and sends exactly the same body/command ID after fresh session/CSRF. Even a definite HTTP rejection remains conservative because earlier uncertain attempts may have committed. The server remains authoritative for current participant mapping and idempotency. The host must preserve/reconcile blocked intent rather than create a replacement ID to bypass it.

`pending` returns a detached copy of command metadata (no credentials or CSRF). `dispose()` permanently closes this client, aborts active exchange and prevents late state acceptance while retaining pending metadata for host review. A changed local actor in a fresh session permanently closes the client. The host MUST dispose on logout, identity, purpose or deployment-policy change, including changes during a request; an unchanged actor ID does not prove unchanged session/purpose. The HTTP protocol does not bind the review and POST atomically across session changes or downstream actions.

Pending state is MEMORY ONLY; reload/crash recovery is not implemented. Do not silently recreate a client or lose unresolved commands on navigation. A read failure invalidates the internal viewed review. Fresh session alone performs no write and a failed session before the first POST creates no pending command. Exchange deadlines, byte (256 KiB), chunk (4096), UTF8, JSON/media, no-store and redirect checks bound untrusted responses, sanitize errors and close owned signals. A timeout cannot preempt blocked JavaScript, undo a callback/server effect or certify SQL rollback. Begun server transactions may finish after client cancellation.
