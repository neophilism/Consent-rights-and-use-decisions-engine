# Participant consent offers

`PermissionRegistry.createOffer` stores a manager-authored disclosure and exact permission terms as a proposal, not consent. A trusted host binds authenticated human identities to subjects through the registry policy. `reviewOffer` returns only an offer belonging to that participant and its current consent, if any. It does not enumerate resources or other participants.

`respondToOffer` requires the viewed offer revision and digest. Acceptance additionally requires `acknowledged: true`; decline does not require an affirmative acknowledgement. The registry atomically stores a deterministic consent, resolved offer, audit assertion and impact event. Retry the same command ID and exact input after uncertain acknowledgement; do not invent a new ID. Expired, cancelled, already resolved or stale offers cannot create another consent. `cancelOffer` cancels only unanswered proposals and never withdraws accepted consent. The existing participant-scoped `withdraw` method withdraws current consent.

The digest binds the exact disclosure and terms, not actual reading, comprehension, legal capacity or freedom from coercion. A manager may still record supplied consent evidence through the older evidence-recording API; that is a separate authority and must not be presented as participant self-capture. No proposal or consent grants copyright or release authorization.

Ten new restricted-role PGlite integration groups exercise exact review, privacy/authority, expiry, terminal responses, replay and revoked mappings, lost commit acknowledgement, post-insert rollback, invalid proposals, caller-input mutation and concurrent responses. Accepted consent participates in normal stored use decisions; withdrawal blocks subsequent evaluation. Concurrency here is within one embedded driver; independent network sessions remain unqualified. No participant HTTP endpoint, invitation delivery, login, identity verification, browser UI, live database contention or live acceptance is provided. Do not expose the Database, registry manager methods or deployment identity mappings directly to a participant. The host must authenticate each request, supply current time and context, implement session/CSRF controls and present exact terms accessibly without presupposed acceptance. No real participants or communications were used.

The offer has no edit operation. If terms change, cancel an unanswered offer and create another with a new ID. Use the review result's exact digest and revision. Never preselect acceptance. Render disclosure as text, not executable markup. Distinguish `responseOpen` (the proposal can receive a response) from an already captured consent's active time window. The original `offer.consent` is a historical exact binding; `review.consent` is the current revision and can be withdrawn. Reconciliation of a cached accepted response returns the original receipt, never a fresh permission. Manager creation is also reconcilable after its response deadline.

The host must refresh identity mappings and recreate a registry when policy changes; an instance snapshots its policy. Mapping removal is checked before cached response/withdrawal return. This is not distributed revocation or atomic fencing of an external effect. Audit records preserve acknowledgement as an assertion, not a digital signature. Generic persistence audit/outbox is in this engine's dedicated database. Offer response events contain exact references, not the disclosure or participant mapping, and do not dispatch communications.
